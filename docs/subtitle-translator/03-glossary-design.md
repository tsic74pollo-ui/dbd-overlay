# DBD 用語辞書 — 設計と運用方針

対象: 仕様書 §16（DBD 用語辞書）/ §17（将来の DBD スラング翻訳）
ステータス: 設計フェーズ。データ本体は [`glossary/dbd-core.yaml`](./glossary/dbd-core.yaml)

---

## 1. なぜ辞書が必要か —— 決定的な実例

韓国 DBD コミュニティに **탕수육（タンスユク＝酢豚）** という隠語がある。意味は「宝箱漁り」。

由来は「みんなが자장면（ジャージャー麺＝発電機）を食べているのに、空気を読まず
탕수육（酢豚＝宝箱）ばかりつまんでいる」という比喩。

| 処理 | 出力 | 評価 |
| --- | --- | --- |
| 機械翻訳 | 「酢豚」 | **意味不明** |
| 辞書置換のみ | 「宝箱」 | 惜しいが、非難のニュアンスが消える |
| **本ツールの目標** | 「またチェスト漁ってる」 | ✅ 日本の DBD プレイヤーが自然に理解できる |

同様に **김풍（キムプン）** は Dwight Fairfield の韓国式あだ名（同名の韓国の漫画家に似ているため）。
機械翻訳は「キムプン」と出力するが、日本のプレイヤーには何のことか伝わらない。正解は「ドワイト」。

**この2例が本プロジェクトの存在理由そのもの。** 単語対応表だけでは足りず、
「直訳してはいけない」というメタ情報と、置き換え後の自然な日本語表現が要る。
それを構造として持つのが本辞書。

## 2. 設計原則

| # | 原則 | 理由 |
| --- | --- | --- |
| 1 | **辞書は「置換器」ではなく「LLM への文脈供給源」** | 機械置換だと「酢豚→宝箱」止まりで、非難のニュアンスが落ちる。LLM に意味と使われ方を渡し、訳文全体を組み立てさせる |
| 2 | **多言語の原語 → 日本語の1エントリに集約** | 韓 `키캠` と英 `face camping` は同じ概念。言語ごとに別辞書を作ると保守が破綻する（§16） |
| 3 | **手書きする範囲を限定する** | キラー名・パーク名はパッチごとに増える。**自動取り込み**にし、人手は「スラング」に集中する |
| 4 | **出典と検証状態を必ず持つ** | 裏取りできていない語を「確定」として LLM に渡すと、誤訳を確信をもって出力する事故になる |
| 5 | **辞書はプロジェクトに埋め込まず参照する** | 辞書更新が既存プロジェクトに反映される。ただし翻訳時に使った辞書バージョンは記録する（再現性・§31） |

## 3. スキーマ

```yaml
version: 1
updated: "2026-08-10"

entries:
  - id: chest-looting-ko            # 一意。kebab-case
    category: slang                 # 下記カテゴリ表を参照
    ja:
      canonical: "チェスト漁り"       # 日本 DBD コミュニティで自然な表現
      aliases: ["宝箱漁り", "箱開け"]
    source_terms:                   # 多言語の原語（§16）
      ko: ["탕수육"]
      en: ["chest looting", "looting chests"]
    literal_trap: "酢豚"             # ★ 直訳するとこうなる、という警告
    do_not_translate_literally: true
    nuance: "「発電機を回さず宝箱ばかり開けている」という非難・呆れのニュアンスを含む"
    note: "由来は「みんなジャージャー麺(発電機)を食べているのに酢豚(宝箱)ばかりつまむ」"
    confidence: verified            # verified | needs_review | unverified
    sources:
      - "https://namu.wiki/w/DEAD%20BY%20DAYLIGHT"
```

### フィールド定義

| フィールド | 必須 | 用途 |
| --- | --- | --- |
| `id` | ✅ | 一意識別子。`glossaryMatches` から参照される |
| `category` | ✅ | 下表参照 |
| `ja.canonical` | ✅ | 日本語の推奨訳。**訳文に実際に出したい表現** |
| `ja.aliases` | | 表記ゆれ。ユーザーが手編集で使った語を吸収する |
| `source_terms.<lang>` | ✅ | BCP-47 言語コードごとの原語（配列） |
| `literal_trap` | | 直訳した場合の誤り例。**LLM への負例として効く** |
| `do_not_translate_literally` | | `true` なら翻訳プロンプトで強い警告として注入 |
| `nuance` | | 感情・態度（非難、賞賛、皮肉など）。訳文のトーンを決める |
| `note` | | 由来・背景。人間のレビュー用 |
| `confidence` | ✅ | `verified` 以外は LLM に「参考情報」として弱く渡す |
| `sources` | | 出典 URL |

### カテゴリ

| カテゴリ | 内容 | 取得方法 |
| --- | --- | --- |
| `killer` | キラー名 | **自動取り込み** |
| `survivor` | サバイバー名 | **自動取り込み** |
| `perk` | パーク名 | **自動取り込み** |
| `addon` / `offering` / `item` | アドオン・オファリング・アイテム | **自動取り込み** |
| `map` | マップ・realm 名 | **自動取り込み** |
| `mechanic` | ゲーム内公式用語（フック、発電機、ゲート、板 等） | 手書き（少数・安定） |
| `strategy` | 戦術用語（キャンプ、トンネル、ループ 等） | 手書き |
| `slang` | コミュニティ隠語 | **手書き。ここが本命** |
| `player` | プレイヤー名・配信者名 | プロジェクト単位でユーザーが追加 |

## 4. 自動取り込み（手書きしない範囲）

キラー・サバイバー・パーク・アドオン・マップ名は DBD のパッチごとに増え続ける。
2026年時点でパークだけで数百件あり、**手書き管理は必ず破綻する。**

### 方針
公式クライアントは英語版と日本語版で同一の内部 ID を持つ。よって
**「英語名 ↔ 日本語公式名」は機械的に対応付けられる。**

```
取得元候補（Phase 2 で決定）
├── Dead by Daylight Wiki（Fandom）の言語別ページ
├── コミュニティが公開している perk 対訳表
└── ゲームのローカライズファイル（利用可否は要確認）
```

`tools/glossary-import.ts` として実装し、生成物を
`glossary/generated/entities.yaml` に出力する。**生成ファイルは手編集しない。**

```
glossary/
├── dbd-core.yaml            ← 手書き。slang / strategy / mechanic
├── generated/
│   └── entities.yaml        ← 自動生成。killer / perk / map …
└── projects/
    └── <project>.yaml       ← プロジェクト固有（プレイヤー名など）
```

### 注意
取得元のライセンスと利用規約を Phase 2 着手時に確認する。
Fandom は CC-BY-SA のため、**生成物を再配布する場合は帰属表示が必要**。
再配布せず「初回起動時にユーザー環境で生成する」方式ならこの制約を回避できる ——
こちらを既定とする。

## 5. 翻訳パイプラインでの使われ方

```
原文セグメント（+ 前後文脈）
   ↓ ① 辞書マッチング（TypeScript 側・LLM 呼び出し前）
   │    ・source_terms を対象言語で全文検索（正規化後）
   │    ・ヒットしたエントリを収集 → segment.metadata.glossaryMatches に記録
   ↓ ② プロンプト構築
   │    ・ヒットしたエントリ「だけ」をプロンプトに注入（全件は入れない）
   │    ・do_not_translate_literally は強い警告として別枠で提示
   ↓ ③ LLM 翻訳（構造化 JSON 出力）
   ↓ ④ 検証
        ・ヒットしたエントリの ja.canonical / aliases が訳文に現れているか
        ・literal_trap の語が訳文に混入していないか → 混入なら reviewStatus="flagged"
```

**④ が効く。** 「酢豚」が訳文に出たら自動でフラグが立つ。
LLM が辞書を無視したケースを機械的に検出できる。

### なぜ辞書全件をプロンプトに入れないのか
全件だと数万トークンになり、コストが跳ね上がるうえ精度も落ちる（無関係な語が注意を奪う）。
**ヒットしたエントリのみ**注入すれば、1セグメントあたり数件で済む。
一方、共通のシステムプロンプトはプロンプトキャッシュに載せる（計画 §3.2）。

## 6. 初期データの方針

`glossary/dbd-core.yaml` に収録するのは以下に限る。

1. **直訳すると意味が壊れる語**（最優先）
2. **日本語コミュニティに定着した呼称がある語**（英語のまま出すと不自然になる）
3. **感情・非難のニュアンスを持つ語**（トーンの再現に必要）

逆に、`generator` → 「発電機」のような**そのまま訳して問題ない語は入れない**。
LLM は既に正しく訳せるため、辞書に入れてもトークンを消費するだけになる。

### 言語別の検証状況

| 言語 | 状況 |
| --- | --- |
| 英語 | 一次情報が豊富。`verified` で収録可能 |
| 韓国語 | 나무위키・DC インサイド ギャラリーから確認済みの語のみ `verified`。それ以外は `needs_review` |
| ドイツ語 / フランス語 / スペイン語 | **未着手**。英語由来のカタカナ語がそのまま使われる傾向があり、専用エントリは少ない見込み。Phase 2 で調査 |

**未検証の語を推測で埋めない。** 空欄のほうが、誤った確信より安全（原則: 設計原則4）。

## 7. 今後の拡張（Phase 2 以降）

- **話者ごとの口調**: `player` カテゴリに `speech_style`（「敬語」「砕けた口調」など）を持たせ、話者分離（Phase 3）と結合する
- **用語の自動候補抽出**: 翻訳時に「辞書にないが繰り返し出現する未知語」を検出し、ユーザーに辞書追加を提案する
- **辞書の共有**: エクスポート/インポートで、コミュニティが辞書を持ち寄れるようにする
