# Phase 0 — ASR ベンチマーク計画

仕様書 §9.3 / 原則2「ASR を決め打ちしない」に対する実施計画。
**このベンチマークを完了するまで MVP 採用 ASR を確定しない。**

---

## 1. 目的

一般的な多言語 ASR ベンチマーク（Common Voice / FLEURS 等）は**朗読音声**が中心で、
DBD 動画の実態 —— ゲーム BGM が鳴り続け、Discord VC の帯域が狭く、叫び声と早口が混ざる ——
とはかけ離れている。

実際、公開ベンチマークで Whisper large-v3 を上回る Canary-1B-v2 / Parakeet-TDT-v3 は
**欧州 25 言語専用で韓国語に対応しておらず**、本プロジェクトの要件を満たさない。
「ランキング上位＝最適」ではないことが既に判明している以上、自前の評価が必要。

---

## 3. 評価用データセット

各クリップ **2〜3 分**。正解書き起こしは**冒頭 60 秒分のみ**作成すれば十分（WER 算出に足りる）。

| ID | 内容 | 検証したいこと |
| --- | --- | --- |
| `en-clean` | 英語 DBD 実況、BGM 控えめ | ベースライン精度 |
| `ko-vc` | 韓国語 VC 会話 | **韓国語精度（最重要・独立の合格基準）** |
| `eu-de` または `eu-fr` | ドイツ語 or フランス語 DBD 動画 | EU 圏言語の実力 |
| `game-loud` | ゲーム音（心音・チェイス曲）が大きい区間 | **ハルシネーション耐性** |
| `vc-clear` | VC が明瞭な区間 | 上限性能 |
| `vc-multi` | 複数人が同時に喋る区間 | 同時発話時の崩れ方（MVP スコープ外だが挙動を知る） |

**正解データの作り方**: 冒頭 60 秒を手で書き起こす。話者が変わる箇所には `[SPK]` マーカーを入れ、
将来の話者分離評価にも再利用できる形にしておく。

## 4. 測定指標

### 4.1 定量

| 指標 | 算出方法 | 備考 |
| --- | --- | --- |
| **WER**（英・独・仏等） | `jiwer` で正規化後に算出 | 小文字化・句読点除去の統一ルールを適用 |
| **CER**（韓国語） | 文字誤り率 | 韓国語は単語分割が不安定なため WER より CER が適切 |
| **ハルシネーション率** | 無音・BGM のみ区間で出力された文字数 ÷ 総文字数 | `game-loud` クリップで測る。**最重要指標のひとつ** |
| **タイムスタンプ誤差** | セグメント開始時刻の正解との平均絶対誤差（秒） | 目標: 中央値 < 0.3 秒 |
| **RTF**（Real Time Factor） | 処理時間 ÷ 音声長 | 小さいほど速い |
| **ピーク VRAM** | `nvidia-smi` サンプリング | 実測値を記録 |
| **言語自動判定の正解率** | 検出言語が正しいクリップ数 ÷ 総数 | コードスイッチ時の挙動も記録 |

### 4.2 定性（人手・3 段階評価）

- 固有名詞（キラー名 / パーク名）の聞き取り具合
- 叫び声・早口・被り気味の発話への耐性
- セグメント区切りの自然さ（字幕として使えるか）

---

## 5. 合格基準（MVP 採用ライン）

**すべて満たすこと**（1 項目でも欠けたら不採用、または API フォールバック併用を検討）:

1. **韓国語 CER ≤ 25%**（人間が読んで修正できる水準）
2. **英語 WER ≤ 20%**
3. **EU 圏言語 WER ≤ 30%**
4. **ハルシネーション率 ≤ 5%**（`game-loud` にて）
5. **タイムスタンプ誤差の中央値 ≤ 0.5 秒**
6. **RTF ≤ 0.5**（30 分動画を 15 分以内で処理）
7. **ピーク VRAM ≤ 8 GB**（RTX 4060 SUPER 16GB に余裕をもって収まる）
8. **ライセンスが商用配布可能**（MIT / Apache-2.0 等）

> 数値は本ベンチマークの初回結果を見て調整する前提の初期案。
> 重要なのは「基準を先に決めてから測る」ことで、後付けで基準を緩めないこと。

## 6. ベンチマークハーネス

```
bench/
├── clips/                  # 評価用クリップ（Git 管理外。取得手順のみコミット）
├── reference/              # 正解書き起こし（*.txt）
├── providers/              # 評価対象 Provider の薄いラッパー
├── run_bench.py            # 全 Provider × 全クリップを実行し JSON 出力
├── score.py                # WER / CER / ハルシネーション率 / タイムスタンプ誤差を算出
└── report.py               # Markdown 比較表を生成
```

**このハーネスは使い捨てにしない。** Phase 1 以降、ASR Provider を追加・更新するたびに
回帰テストとして再実行する。

## 8. 想定期間

約 1 週間。内訳: クリップ収集と正解作成 2 日 / ハーネス実装 2 日 / 実行と評価 2 日 / レポート 1 日。

**Phase 1 の実装はこの完了を待つ必要がない** —— `ASRProvider` 抽象と `MockProvider` があれば
パイプラインの骨格は並行して作れる。ベンチマークの結果は「既定 Provider をどれにするか」の
設定値として最後に差し込む。
