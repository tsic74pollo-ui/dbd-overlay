# 翻訳レイヤー — プロンプトと構造化出力の設計

対象: 仕様書 §14（翻訳エンジン）/ §15（翻訳コンテキスト）/ 原則3（翻訳と字幕生成の分離）
ステータス: 設計フェーズ。実装は Phase 2

---

## 1. この設計が守るべき制約

| # | 制約 | 設計への反映 |
| --- | --- | --- |
| 1 | **翻訳 AI に字幕レイアウトを決めさせない**（原則3） | 出力スキーマに改行・行数・表示時間を**含めない**。LLM は「意味」だけを返す |
| 2 | **原文を必ず保持**（原則4） | LLM に原文を書き換えさせない。出力は `id` と訳文のみで、原文は TypeScript 側が保持 |
| 3 | **セグメントを独立に翻訳しない**（§15） | 前後のセグメントを文脈として渡す。ただし**翻訳して返すのは対象セグメントだけ** |
| 4 | **Provider ロックインしない**（§14） | JSON Schema による構造化出力という、各社共通で表現できる機能だけを使う |
| 5 | **辞書は置換器ではない**（§16-17） | ヒットしたエントリを「文脈」として渡し、訳文全体を LLM に組み立てさせる |

---

## 2. リクエスト単位

**1 リクエスト = 連続する 25 セグメント**（翻訳対象）＋ 前後 3 セグメント（文脈のみ）。

```
[ctx -3][ctx -2][ctx -1] │ [seg 1] … [seg 25] │ [ctx +1][ctx +2][ctx +3]
                          └── 翻訳して返す範囲 ──┘
```

- 小さすぎると文脈が切れ、大きすぎると1件の誤りが広範囲に波及する。25 は暫定値で、Phase 2 で調整する
- チャンク境界が会話の途中に落ちても、前後3件の文脈で吸収できる
- 直前チャンクの**確定訳**も渡す（`recent_translations`）。呼称や口調の一貫性が保たれる

## 3. プロンプト構成とキャッシュ設計

プロンプトキャッシュはプレフィックス一致で効くため、**変化しないものを前に置く**。

```
┌─ キャッシュ対象（毎回同一 → キャッシュ読み取り ≒ 0.1 倍） ─┐
│ ① システムプロンプト（役割・翻訳方針・禁止事項）              │
│ ② 出力形式の説明と few-shot 例                              │
└──────────────────────────────────────────────────────────┘
┌─ 毎回変わる（キャッシュ境界より後ろ） ────────────────────┐
│ ③ ヒットした辞書エントリ（そのチャンクの分だけ）              │
│ ④ 直前チャンクの確定訳                                      │
│ ⑤ 文脈セグメント ＋ 翻訳対象セグメント                       │
└──────────────────────────────────────────────────────────┘
```

② の直後に `cache_control` を置く。①②は数千トークンあるが、2回目以降は課金がほぼ消える。

> 辞書全件（数万トークン）をプロンプトに入れてはいけない。コストが跳ねるうえ、
> 無関係な語が注意を奪って精度が落ちる。**ヒットしたエントリのみ**注入する。

## 4. システムプロンプト（案）

```
あなたは Dead by Daylight（DBD）のゲームプレイ動画を日本語へローカライズする翻訳者です。
日本の DBD プレイヤーが読んで自然に理解できる日本語を作ることが仕事です。

## 前提
- 入力は動画から自動文字起こしした発話です。言い淀み、言い間違い、
  音声認識の誤りが含まれます。
- 発話は試合中のボイスチャットが中心で、短く、断片的で、口語です。

## 翻訳方針
- 逐語訳ではなく、日本の DBD コミュニティで実際に使われる表現に置き換えてください。
- ゲーム用語は日本語版クライアントの公式名称、または日本語コミュニティで
  定着した呼称を使ってください（例: pallet →「板」、hook →「フック」「吊る」）。
- 話し言葉として訳してください。試合中の短い掛け合いに「〜であります」のような
  硬い文体は使いません。
- 話者の感情（焦り、苛立ち、喜び、皮肉）を訳文に残してください。
  非難のニュアンスを持つ語を、中立的な描写に薄めないでください。
- 前後の発話を読み、会話として成立する訳文にしてください。
  「どこ？」「左」のような短い応答は、直前の発話を踏まえて訳します。

## 禁止事項
- 原文にない情報を足さないでください。
- 訳文に改行を入れないでください。行数・改行位置・表示時間は
  後段の別処理が決めます。あなたは意味だけを担当します。
- 説明や注釈を訳文に混ぜないでください。補足は notes フィールドに書きます。
- 聞き取れていない箇所を推測で埋めないでください。
  自信がない場合は confidence を下げ、notes に理由を書いてください。

## 音声認識の誤りへの対処
明らかな認識ミスは、文脈から意図を推定して訳して構いません。
その場合は必ず notes に「原文の〇〇は△△の誤認識と判断」と記録してください。
```

**改行禁止を明示している点が要**。ここを緩めると LLM が勝手に `\n` を入れ、
字幕品質層の計算が壊れる。

## 5. 出力スキーマ

```json
{
  "type": "object",
  "properties": {
    "translations": {
      "type": "array",
      "items": {
        "type": "object",
        "properties": {
          "id":         { "type": "string" },
          "text":       { "type": "string", "description": "日本語訳。改行を含めないこと" },
          "confidence": { "type": "number", "description": "0.0-1.0" },
          "notes":      { "type": "string", "description": "推定した箇所・判断根拠。無ければ空文字" },
          "glossary_used": {
            "type": "array",
            "items": { "type": "string" },
            "description": "実際に使用した辞書エントリの id"
          }
        },
        "required": ["id", "text", "confidence", "notes", "glossary_used"],
        "additionalProperties": false
      }
    }
  },
  "required": ["translations"],
  "additionalProperties": false
}
```

**含めないもの**（意図的）:
`start_time` / `end_time` / `lines` / `line_break` / `duration`
—— すべて字幕品質層（TypeScript）の責務。LLM に触らせない。

`glossary_used` を返させることで、**LLM が辞書を実際に見たかを検証できる**。
辞書がヒットしていたのに `glossary_used` が空なら、フラグを立てる根拠になる。

## 6. few-shot 例

辞書の威力が出る2例を入れる。

### 例1 — 韓国語スラング（直訳が壊滅する）

```
入力:
  文脈: [-1] "발전기 두 개 남았어"
  対象: [S12] "야 쟤 또 탕수육 먹고 있어"
  辞書: chest-looting-ko（ja.canonical="チェスト漁り",
        literal_trap="酢豚", nuance="非難・呆れ")

出力:
{"id":"S12","text":"おいアイツまたチェスト漁ってる","confidence":0.9,
 "notes":"","glossary_used":["chest-looting-ko"]}
```

「酢豚」と訳さないこと、かつ「またアイツ〜」で呆れのニュアンスを残すことを同時に示す。

### 例2 — 文脈依存の短い応答

```
入力:
  文脈: [-1] "Killer's coming, where do I go?"
  対象: [S45] "Left, left! Loop the shack!"

出力:
{"id":"S45","text":"左、左！ 小屋で板グル！","confidence":0.85,
 "notes":"","glossary_used":["looping"]}
```

`loop` を「ループする」ではなく「板グル」にする、を示す。

### 例3 — 音声認識の誤りを notes に残す

```
入力:
  対象: [S78] "he has no wed hard"

出力:
{"id":"S78","text":"あいつデッハ持ってない","confidence":0.6,
 "notes":"原文の 'no wed hard' は 'Dead Hard' の誤認識と判断",
 "glossary_used":[]}
```

推測したことを隠さない、を示す。`confidence` が低いので後段でレビュー対象になる。

## 7. 翻訳後の自動検証（TypeScript 側）

LLM の出力を無条件に信用しない。以下を機械的にチェックする。

| チェック | 違反時の動作 |
| --- | --- |
| 全 `id` が揃っているか（欠落・余剰） | エラー。チャンクを再試行 |
| `text` に改行が含まれていないか | 改行を除去し、`flagged` |
| ヒットした辞書の `literal_trap` が訳文に含まれていないか | `flagged`（例: 訳文に「酢豚」） |
| ヒットした辞書の `ja.canonical`/`aliases` が訳文にあるか | 無ければ `flagged`（辞書無視の疑い） |
| `confidence` が閾値（既定 0.7）未満 | `flagged` |
| 訳文が空、または原文と同一 | `flagged` |

`flagged` になったセグメントはレビュー画面で上部に集約し、人間が優先確認する。
**機械が形式を検証し、人間が意味を確認する** —— リファレンス実装の責務分担をそのまま採る。

## 8. 再翻訳のモード

仕様書 §22 が要求する2種類を区別する。

| モード | 入力 | 用途 |
| --- | --- | --- |
| **再翻訳** | 原文 + 現在の訳文 + ユーザー指示（任意） | 「もっと砕けた口調で」など、方向を指定して直す |
| **原文から再翻訳** | 原文のみ（現在の訳文を捨てる） | 訳文が的外れなときに白紙からやり直す |

再翻訳は 1 セグメント単位のため、**モデルを Claude Opus 5 に上げる**選択肢を UI に出す。
バルクは Sonnet 5、難所だけ Opus 5、というコスト配分にする。

## 9. Provider 抽象

```ts
interface TranslationProvider {
  readonly id: string;                    // "claude" | "gemini" | "openai" | "mock"
  readonly model: string;
  translate(req: TranslationRequest): Promise<TranslationResult>;
  estimateCost(req: TranslationRequest): CostEstimate;
}
```

- 各 Provider は §5 のスキーマで検証済みの結果を返す責務を持つ
- **`MockProvider`**（原文をそのまま返す / 固定訳を返す）を必ず用意する。
  これが無いと GPU も API キーも無い CI で E2E テストが回らない
- `estimateCost` により、実行前に推定コストを UI 表示できる
